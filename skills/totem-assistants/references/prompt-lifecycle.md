# Prompt drafting and publication

Read this for prompt-content changes and exact-version publication.

Read get_team_business_knowledge before authoring or testing. Resolve missing, materially incomplete or contradictory facts from supplied evidence. Within an authorized authoring task, prepare preview_save_team_business_profile when the canonical profile needs repair before dependent work.

The profile is authoring evidence, not automatically delivered runtime knowledge. Include every business fact the assistant must state in its semantic brief. Opening hours belong in team settings through preview_set_weekly_opening_hours, never prompt prose. Notes, Team Library and retrieval knowledge remain separate from the canonical profile.

For content-only changes, send the semantic business change and exact current handle/version clocks required by the family draft tool. Never send a raw prompt, patch, BASE policy, evidence object, custom tool schema, provider binding or voice topology in this lane. Totem authors and stores the immutable version.

Inspect the stored draft. Run tests on that exact version only on an explicit originating human request to execute them; existing cases, stale evidence, or a returned review contract do not authorize execution. A request to create or edit a prompt authorizes neither a test run nor retries. Preserve a request to leave it as a draft. A same-team Native Voice successor uses its returned source_handle to preserve eligible custom functions and voice; a prompt version is not a structural successor.

Publish the inspected stored version by exact number and fresh concurrency clocks. Publication must not regenerate it. Preserve failed, stale, missing or unrun evidence and follow returned warning decisions rather than inventing green. Wait for terminal status, then fresh-read the active prompt/runtime. Retain the original status handle after a lost response.
